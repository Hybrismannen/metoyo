# 11 — Pius Lineage & System Boundary

## 1. Why this file exists

The Gift Whisperer was not developed in isolation. Historical source documents explicitly place parts of its development inside the wider **Pius** architecture, including PIUSInn / InnOVA and Aftermath Placenta (APz) language.

METOYO, however, must remain intelligible as a project in its own right.

This file preserves the lineage without making the public ritual space dependent on users understanding Pius.

## 2. Historical Pius references

The 2025 project material includes formulations such as:
- "Produced by PIUSInn Labs — APz Protocol Deployment Document";
- use of the InnOVA development arc;
- classification of the project as a lightweight memory-invocation / relational-ritual-prompt system;
- Pius-based architecture described as part of the intellectual structure beneath the interface.

These references document **development provenance**.

## 3. Current boundary

```text
PIUS
wider process / epistemic / system-development framework
        │
        │ historical development lineage
        ▼
METOYO
public-facing ritual condition and project
        │
        ▼
THE GIFT WHISPERER
internal ritual / prompt / execution engine
```

METOYO should not require a public user to understand:
- Pius terminology;
- APz;
- PIUSInn;
- EPSc;
- Atmos;
- Pius agents;
- other Codex modules.

Those may remain useful for internal process design, provenance, audit, or future engineering.

## 4. Gift Whisperer as internal actor

The canonical naming directive describes The Gift Whisperer as a **working dwarf**: an internal actor performing the work without claiming the stage.

A future implementation may make this internal actor more agentic, but such evolution should be treated as a METOYO architecture decision and not automatically fused with unrelated Pius agent frameworks.

## 5. HARP influence

Pius Codex 5.0 contains the **Harvard Reference & Source Audit Protocol (HARP)** with explicit attention to:
- referencing standard;
- source verification;
- reference audit;
- audit workflow;
- editorial integration;
- enforcement.

METOYO adopts the underlying discipline through:
- [SOURCE_INDEX.md](../SOURCE_INDEX.md);
- explicit evidence types;
- preservation of historical source extracts;
- distinction between project decisions, hypotheses, plans and externally verified claims;
- no silent upgrading of poetic/narrative statements into empirical facts.

See [Editorial & Source Protocol](12-editorial-source-protocol.md).

## 6. InnOVA lineage

Historical roadmap documents used an InnOVA six-stage development arc:

```text
Initiate
Navigate
Nurture
Optimize
Verify
Activate
```

This remains useful as historical process architecture but is not required as the public-facing roadmap vocabulary.

## 7. APz lineage

The source corpus's APz language indicates that The Gift Whisperer was treated as a deployed outcome/artifact emerging from a wider Pius process.

In this repository, the practical consequence is provenance rather than dependency:
- preserve where the design came from;
- keep the operational model independently specifiable;
- avoid importing unrelated Pius machinery unless a current METOYO requirement needs it.

## 8. Canonical rule

> Pius may explain part of how METOYO was designed. It does not replace what METOYO is.

The public project remains METOYO.  
The internal ritual engine remains The Gift Whisperer.
